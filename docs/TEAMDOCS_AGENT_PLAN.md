# TeamDocs Agent 改造计划

> 制定日期：2026-09-20。
> 依据：当前工作区源码、未提交改动及本次后端测试结果。
> 文档性质：推荐实施方案，不代表以下功能已经完成。本次只制定计划，不修改业务代码。

## 1. 核心结论

**不要推倒重写 TeamDocs。将现有文档协作平台升级为“具有空间权限、来源引用和受控操作能力的团队文档 Agent”。**

原来的空间、成员、文件、标签、预览和审计不是旧包袱，而是 Agent 可以安全调用的业务底座。新增的核心是：让模型根据用户目标选择工具，读取结果，决定是否继续检索或读取文档，最终给出可追溯的回答或待确认的操作建议。

推荐顺序：

1. 完成文档解析和正文分块，让系统真正读得到文档。
2. 建立带空间权限和来源定位的正文检索。
3. 完成有次数、时间和上下文限制的单 Agent 工具调用循环。
4. 接入会话、运行状态、引用和前端交互，发布只读 MVP。
5. 增加“用户确认后添加已有标签”这一种写操作，形成行动闭环。
6. 根据评测结果决定是否增加向量检索，不为了技术名词提前堆基础设施。

**项目定位建议：**

> TeamDocs 是面向小型团队的文档协作与知识 Agent 平台。在空间权限约束下，支持资料检索、多文档归纳、来源追溯，以及人工确认后的文档整理操作。

### 1.1 这份计划采用的边界

1. 保留 Java 后端和 Vue 前端，不另起 Python 服务，不迁移为通用 Agent 平台。
2. 继续以个人开发、可解释、可测试和单机 Compose 部署为目标，不预设大规模企业场景。
3. 一个会话固定属于一个用户、一个空间；首版不允许跨空间问答和共享会话。
4. 模型供应商、精确版本和费用上限尚未由需求指定，作为接入阶段的配置和验证项，不在此假装已经确定。
5. 以下范围和工期是建议，不是用户已经确认的产品需求或上线承诺。

## 3. 目标场景与版本边界

### 3.1 必须能演示的场景

1. **找资料并回答。** 用户问“本项目上线前需要做哪些检查？”Agent 查找相关文档、读取命中段落，按条目回答并附来源。
2. **多文档归纳。** 用户问“比较这两份接口约定的差异。”Agent 分别读取两份文档，标注一致、冲突和未说明的内容，不擅自决定哪份有效。
3. **多轮追问。** 用户继续问“第二点在哪份文档里？”Agent 在同一空间和会话中定位引用；切换空间后不沿用旧上下文。
4. **承认证据不足。** 没有资料、正文未解析或只检索到部分内容时，说明限制，不把模型常识伪装成项目事实。
5. **确认后整理。** 后续版本中，Agent 建议给某文档添加一个已有标签；用户查看操作卡片并确认后，后端才执行。

### 3.2 MVP 与后续版本

| 版本 | 必做范围 | 明确不包含 |
|---|---|---|
| V0.1：只读 Agent | 支持格式解析、正文检索、工具循环、单空间会话、引用、运行记录、错误与预算控制 | 写操作、跨空间搜索、自动联网 |
| V0.2：受控操作 Agent | 在 V0.1 上增加已有标签推荐、人工确认、幂等执行和审计 | 批量移动、删除、成员管理、文件覆盖 |
| V0.3：按效果优化 | 若检索评测不达标，再验证向量检索、混合召回或重排 | 为展示技术栈而默认引入全部组件 |

不纳入当前主线：多 Agent 协作、MCP Server、插件市场、长期自主任务、浏览器控制、任意代码执行、微服务拆分、实时协同编辑、OCR、复杂表格计算和知识图谱。

**Agent 不等于必须有写权限或向量库。** V0.1 的关键是模型能够根据工具结果决定下一步，而不是每次固定“搜索一次后总结”。与此同时，单个聊天接口或固定 RAG 流水线也不能被描述成已完成完整 Agent 改造。

## 4. 技术路线

### 4.1 推荐选型

| 领域 | 推荐方案 | 取舍 |
|---|---|---|
| 模型接入 | Spring AI，先验证与现有 Boot 3.5 匹配的 1.1.x 维护版本 | 复用 Spring 生态；不为 Agent 首先做 Boot 4 大迁移 |
| 编排 | 单 Agent、显式工具执行循环 | 由应用控制权限、次数、超时和追踪，不搭通用工作流引擎 |
| 文档解析 | Apache Tika 为候选；只启用需要的解析器 | 不把前端能预览所有格式误当成后端都能解析 |
| 初始检索 | MySQL 分块正文 FULLTEXT + ngram，结合现有元数据搜索 | 先得到可测的基线，不新增基础设施 |
| 会话和执行记录 | MySQL | 重启后可查历史、终态和确认操作 |
| 运行事件 | Spring MVC SSE；前端用携带 Bearer Token 的 `fetch` 消费 | 保留当前 MVC 架构，不整体迁移 WebFlux |
| 后台解析 | MySQL 持久状态 + 有界执行器 + 定时补扫 | 首版不引入 MQ，避免纯内存任务丢失 |
| 后续语义检索 | 有明确评测收益时再选 Qdrant 等独立向量库 | MySQL 仍是权限与文档状态的事实来源 |

模型接入必须先验证：中文表现、原生工具调用、结构化参数、超时、用量返回、目标环境可达性以及隐私条款。“兼容 OpenAI 协议”不能替代这些测试。首版只接一个供应商，不建设多供应商路由平台。

Spring AI 的版本与 Boot 版本绑定，实施时应按官方兼容关系锁定精确 BOM 和依赖版本，先跑编译、启动及工具调用小验证。不要混用 1.x 与 2.x 示例，也不要假定所有版本的自动工具循环行为一致。如果当前兼容线的维护状态不满足上线要求，单列框架升级任务，不隐藏在业务改造中。

### 4.2 目标结构

```text
Vue 空间工作台 / Agent 页面
    |
    | JWT + 会话请求 + 运行事件
    v
AgentController
    |
    v
AgentRunService：身份、空间、会话、预算、终态
    |
    v
受限工具循环 <----> ChatModel
    |
    v
工具适配层：校验参数、注入可信上下文、限制输出
    |
    +-- 文档/标签现有 Service：复用业务规则与 Spring 代理
    +-- DocumentRetrievalService：正文检索、分页读取、来源构造
    |
    v
```

业务 Service 不需要知道模型如何思考。模型不得直接访问 Mapper、MinIO 凭据或任意 SQL；工具适配层也不能为了方便绕过已有权限。

## 5. 文档解析与正文检索

### 5.1 支持范围

首版支持 UTF-8 TXT、Markdown、文本型 PDF、DOCX。扫描 PDF、加密文件、图片、压缩包、PPT、复杂 Excel 和 OFD 暂不承诺解析；原有上传、下载和预览功能仍保留。

解析应明确区分：成功、有错误，以及格式不支持或没有可提取文本。建议在现有枚举上增加 `SKIPPED`，并保存简短原因；不能出现“扫描 PDF 解析出空文本，却向用户显示可问答”的情况。

### 5.2 处理链路

1. 上传成功并持久化文档后，由 Worker 扫描 `PENDING` 任务；不在上传请求里同步解析，也不依赖请求结束后失效的 `MultipartFile`。
2. Worker 使用条件更新领取任务，设置 `PARSING`、任务版本和开始时间。内存执行器只是加速器，数据库状态才是待办依据。
3. 按数据库中的 object key 读取 MinIO 流，及时关闭；不让客户端或模型提供任意下载 URL。
4. 检测实际文件类型，提取正文，清理明显噪声，按段落切分；PDF 尽可能保留页码，其他格式保留段落或字符偏移。
5. 在短事务中校验任务仍有效，替换分块并设置 `READY`；失败设置 `FAILED` 并保留脱敏原因。
6. 定时检查超时的 `PARSING`，转为失败并允许受权用户重试；首版不做无限自动重试。

初始调参起点：每块约 800～1,200 个中文字符，重叠约 100～150 个字符；对英文长文本、代码和表格单独验证。字符数不等于 Token 数，现有 `token_count` 字段必须统一为估算 Token 语义，或改为准确命名的字符数，不能混用。

### 5.3 必须补齐的一致性约束

1. 建议为 `document` 增加 `parse_version` 和 `parse_started_at`；重试或重新解析递增版本，旧任务不得覆盖新结果。
2. 成功发布、失败回写和超时处理都必须匹配 `documentId + parseVersion + PARSING`。发布时还要检查删除状态及空间有效性；替换分块和设置 `READY` 必须在同一短事务内，条件不匹配时不允许留下新分块。超时已转为 `FAILED` 后，迟到的成功或失败回调均不得覆盖终态。
3. 解析与彻底删除必须围绕同一文档记录协调。删除先完成时旧 Worker 不得重建孤立分块；发布先完成时删除应清理其分块。
4. 软删除可以暂留分块，但所有读取必须过滤文档和空间的删除状态；恢复后只有有效的 `READY` 内容才能参与问答。
5. 首版重新解析期间不提供旧正文；只有当前 `READY` 版本可检索，减少双版本维护复杂度。
6. 重新解析会替换分块。引用须包含文档、分块及解析版本，失效后显示“原引用已更新或不可访问”，不能把旧引用指到新块。
7. 解析新增的状态写入可能触发现有 `document.updated_at` 自动更新时间；必须明确用户可见的“文档修改时间”是否受影响，必要时使用独立解析时间，避免后台任务扰乱最近更新排序。

### 5.4 检索契约

保留原 `/documents/search` 的元数据搜索行为，另增内部正文检索能力，不把原搜索悄悄改成模型调用。

1. 对 `document_content.content` 建 FULLTEXT ngram 索引，并用真实 MySQL 验证中文、英文缩写、停用词和单字限制。
2. SQL 在排序和 LIMIT 前加入 `space_id`、文档与空间有效状态、`parse_status=READY` 等约束；不能全库召回后才由 Java 过滤。
3. 元数据搜索负责找到可能相关的文档，正文检索负责找到有依据的段落；首版由 Agent 选择组合，不必立即做复杂融合排序。
4. 每次返回有界结果，例如 Top 6；合并到运行上下文时去重并执行总长度限制。
5. 输出包含 `documentId`、`chunkId`、`chunkIndex`、`parseVersion`、文档名、位置和文本摘录。
6. 长文档使用分页读取和明确的 `hasMore`；只看部分段落时不得宣称“已完整审阅整份文档”。

## 6. 单 Agent 的行为与工具边界

### 6.1 V0.1 工具白名单

| 工具 | 模型提供的参数 | 返回内容 |
|---|---|---|
| `search_documents` | 关键词、有界页码 | 当前空间的文档元数据，不返回原文件路径 |
| `search_document_chunks` | 查询词、可选候选文档 ID | 当前空间有权限的命中段落及来源 |
| `read_document_chunks` | 文档 ID、起始块、有界数量 | 按顺序的正文片段、来源及是否还有内容 |

摘要、比较、问答是模型基于这些工具完成的任务，不需要各做一个只有 Prompt 的“工具”来凑数量。

V0.2 再增加 `list_tags` 和 `propose_add_document_tag`。后者只生成待确认建议，模型不能直接调用真正的执行接口。

### 6.2 执行循环

1. 验证用户、空间成员资格及会话归属，建立服务端可信运行上下文。
2. 加载当前仍可访问的历史消息，按预算截取；工具结果和文档内容明确标记为不可信数据。
3. 调用模型，获得最终回答或工具调用请求。
4. 后端检查工具白名单、JSON 参数、资源归属、额度和运行取消状态。
5. 执行工具并记录结果摘要，将结果交还模型；允许模型继续查找、读取或结束。
6. 达到次数、时间或上下文上限时停止，返回已经取得的有效信息和未完成原因。
7. 校验来源引用，保存消息和运行终态，再通知前端完成。

选择应用层显式循环时，必须关闭会绕过该循环的框架自动工具执行；不能同时启用两套循环。使用框架现成组件也可以，但前提是能够验证每次调用都经过相同的权限、预算和追踪边界。

首版建议起始上限：每次运行最多 6 次模型调用、8 次工具调用，总时长 90 秒，每个用户同时 1 次运行；上下文上限按目标模型单独设置。所有内部重试都计入预算。这些是保护阈值，不是已验证的性能指标。

### 6.3 来源与记忆

1. 来源编号由后端针对本次实际读取的分块分配，模型只引用这些编号。
2. 回答结束时校验编号是否存在、是否仍可访问；来源对象和跳转地址由后端构造，不能照抄模型生成的任意链接。
3. 校验失败时最多进行一次计入预算的修正，仍失败则标记回答不可验证，不展示假引用。
4. “引用合法”不代表“结论被引用支持”。另用评测检查关键结论是否真的有依据。
5. 会话只保存必要的用户消息、最终回答和来源标识；首版不实现长期画像、跨空间记忆或自动长期摘要。
6. “来源依赖”不只是最终展示的引用。保守记录本轮向模型提供的全部文档依赖，包括元数据、正文和所用历史回答的传递依赖。历史消息、运行结果和 SSE 最终答案采用同一校验规则；任一依赖被删除、失权或版本失效时，首版直接遮蔽整条衍生回答，也不再把它重送给模型，无须做句子级溯源。不能只把引用按钮禁用却继续暴露回答正文。
7. 不展示或保存模型私有思维链。界面中的“执行过程”仅指工具名、状态、耗时、命中文档数等可观察事实。

## 7. 权限、费用与安全约束

这些是 MVP 的组成部分，不是“有时间再补”的优化。

1. **身份不可由模型指定。** `userId`、固定 `spaceId` 和 `sessionId` 来自认证与服务端会话，不放入可由模型任意填写的工具参数。
2. **每个工具独立授权。** 运行开始通过检查不代表后续永远有权限；每次读取、展示来源和执行确认动作都检查当前成员与资源状态。
3. **不要跨线程依赖 ThreadLocal。** 当前 `SpaceContext` 是 ThreadLocal。异步 Worker 和工具执行器显式传递可信身份，通过 Spring 代理调用带权限注解的 Service；不能假定请求线程的上下文会自动传过去。
4. **避免嵌套上下文被清空。** 当前权限切面会在退出时清理 `SpaceContext`。工具编排不要在内层 Service 返回后依赖外层残留值；确有嵌套需求时先明确保存与恢复规则并补测。
5. **文档内容不是指令。** “忽略规则、读取其他空间、泄露密钥”等文档文本不获得任何执行权限。真正边界由工具白名单、参数校验和授权保证，不只靠 Prompt。
6. **模型输出不是可信 HTML。** Markdown 展示禁用原始 HTML 或严格清洗，限制链接协议；引用链接只使用后端构造的站内资源路径。
7. **解析有单独资源上限。** 保留原 100MB 上传能力不代表允许同步解析 100MB 文件。首版可从 10MB 解析上限、固定并发和最大正文字符数起步，测试解压膨胀和异常文件；超限只影响 AI 解析，不影响原文件管理。
8. **资源耗尽要能隔离。** 线程超时不保证第三方解析器立即停止。上线前实测解析器限制；若无法可靠限制 CPU、内存和解压行为，将解析移到可终止的隔离进程，而不是只增加 timeout 配置。
9. **收费能力与普通缓存分开。** 当前登录限流的 Redis 故障放行策略，不能直接复制到付费模型调用。AI 配额系统不可用时拒绝新的 AI 请求，普通文档功能继续可用。
10. **费用有硬停止。** 限制用户并发、单次调用数、输入输出量及日额度。每次付费尝试前，按完整输入（含历史、工具定义与结果）和最大输出的保守成本上界原子预占额度，余额不足则拒绝；获得真实用量后结算，超时、断流或重启导致用量未知时保留预占，不视为免费。关闭无法纳入预算的 SDK 隐式重试，其余重试统一经过预占入口。具体金额阈值须结合选定模型价格配置，估算与真实用量分别记录，不能默认无限。
11. **外部模型存在数据出站。** 首轮验证只用无敏感信息的样例；启用真实空间前说明发送范围及供应商数据政策，并取得相应授权。只发送回答所需片段，不默认上传整个库。
12. **可撤销不等于可收回。** 发送给模型或浏览器后不能承诺收回已经发送的数据。运行过程中失权时中止后续工具与输出，并明确这一边界。
13. **日志不存秘密。** 不记录 API Key、JWT、预签名 URL、全文 Prompt 或整段私有正文；追踪默认保存来源 ID、参数摘要、错误码和用量。

## 8. 数据和接口的最小设计

### 8.1 数据表

在现有 `document` 和 `document_content` 基础上逐步新增：

| 表 | 最小职责 |
|---|---|
| `agent_session` | 用户、固定空间、标题、创建与更新时间 |
| `agent_run` | 会话、请求幂等键、请求摘要、状态、模型标识、耗时、调用次数、用量、错误码 |
| `agent_message` | 用户消息、最终回答、所属运行、来源依赖与时间 |
| `agent_tool_call` | 运行、序号、工具名、脱敏参数摘要、结果摘要、耗时和状态 |
| `agent_action`，V0.2 才建 | 待确认操作的不可变参数、发起人、资源、有效期、幂等状态和执行结果 |

`agent_run` 推荐状态：`QUEUED`、`RUNNING`、`SUCCEEDED`、`FAILED`、`CANCELLED`、`TIMED_OUT`。生成操作建议即可结束该次运行，确认执行是独立业务动作；不为一个标签操作引入复杂的暂停恢复编排系统。

同一会话首版串行运行。对 `(session_id, client_request_id)` 建唯一约束并保存请求内容摘要：同键同内容返回原运行，同键不同内容拒绝，避免网络重试重复计费或消息顺序混乱。

运行中的过程数据可以有界缓存在内存，但会话、用户消息、终态和待确认动作不能只存在内存。进程重启后将无法恢复的旧运行标记为中断失败，不静默重放收费请求。

### 8.2 建议接口

统一前缀：`/spaces/{spaceId}/agent`。这些是建议契约，实施时对齐现有响应与异常风格。

1. `POST /sessions`：创建会话。
2. `GET /sessions`、`GET /sessions/{sessionId}/messages`：分页查询本人会话和可访问历史。
3. `POST /sessions/{sessionId}/runs`：提交问题，带请求幂等键，返回 `runId`。
4. `GET /runs/{runId}`：查询运行快照及最终结果。
5. `GET /runs/{runId}/events`：订阅 SSE，先返回当前快照，再发送运行事件。
6. `POST /runs/{runId}/cancel`：取消后续执行；已消耗的模型费用不能保证撤销。
7. V0.2：`POST /actions/{actionId}/confirm`、`POST /actions/{actionId}/reject`。

解析状态与重试仍放在文档接口下，例如 `GET /documents/{documentId}/parse-status`、`POST /documents/{documentId}/reparse`。重试要求空间权限和既有 OWNER/ADMIN/资源创建者边界，并限制频率。

所有会话、运行和操作 ID 都必须关联校验当前用户与路径空间，不能依靠随机 ID 防越权。

### 8.3 SSE 与前端

1. 最小事件集为 `run_started`、`tool_started`、`tool_finished`、`answer_ready`、`run_finished`、`run_failed`；V0.2 增加 `action_proposed`。
2. 首版先流式显示工具状态，最终答案完成引用校验后整体展示。逐 Token 输出可以随后增加，避免未经校验的来源和失权内容提前渲染。
3. 现有 Axios JSON 封装超时为 10 秒，不直接用于消费长连接。使用独立 `fetch` 流客户端，复用 Token 获取和 401 处理规则。
4. 原生 `EventSource` 不便携带当前 Bearer 请求头，不能把 Token 放进 URL 来规避。
5. SSE 只负责观察运行。断线不自动重新提交问题；重连查询运行快照，首版不承诺逐事件回放。服务端先注册订阅并有界缓冲，再读取和发送快照，最后按递增序号去重发送后续事件；注册、快照和完成通知须协调，避免运行在订阅期间完成却漏掉终态。终态先持久化再通知，订阅已完成的运行时立即返回终态并结束。
6. 用户点击停止才发取消请求；切换空间或会话时关闭旧流，使用 `spaceId + sessionId + runId` 校验事件归属，丢弃过期回调。
7. Nginx 当前的 `proxy_request_buffering off` 不是响应禁缓冲。为 SSE 配置并验证 `proxy_buffering off` 或对应响应头、心跳与超时，同时检查外层反向代理。
8. Spring Security 的异步分派和错误分派需要集成验证，不能通过把整个 Agent 路径设为匿名访问解决 SSE 问题。

## 9. 人工确认操作：只先做一种

V0.2 选择“给一个文档添加一个当前空间已有标签”，暂不创建新标签，不批量修改，不支持删除或授权变更。

1. 模型返回建议，后端校验文档和标签后生成 `agent_action`。
2. 卡片展示文档名、标签名、操作效果和到期时间。用户确认的是这些固定内容，不是一句模糊的“让 Agent 继续”。
3. 确认接口只接收 action ID，不接受前端重新提交可替换的操作参数。
4. 后端再次校验发起人、空间成员资格、现有标签业务权限、文档与标签当前状态。
5. 在同一数据库事务中原子领取待确认动作，通过 Spring 代理调用现有标签 Service，并记录执行结果；拒绝、过期或已完成的动作不能再次执行。
6. 标签关联本身也应满足幂等约束。用户手动已添加同标签时返回“已存在”，不算再次执行一个新动作。
7. 双击、网络重试和服务中断后重试，都返回同一动作结果；数据库更新成功但响应丢失不能造成重复业务效果。
8. 保留原操作日志，并关联 `runId`、`actionId`，区分“模型建议”和“用户确认后实际执行”。

这条链路验证完成前，不开放通用写工具。未来增加移动或重命名时，需要针对新的资源条件和失效规则单独设计，不能简单把全部 Service 方法暴露给模型。

## 10. 分阶段实施与验收

阶段工期按一人、熟悉现有代码估计为有效开发日，不包含全部学习与返工时间；阶段可以调整，但验收门槛不能跳过。

### P0：整理基线和接入验证，1～2 天

1. 检查并保留当前解析基础改动，明确哪些已完成、哪些只是骨架。
2. 为已有数据库设计增量 SQL，不直接执行带 `DROP TABLE` 的初始化脚本。
3. 用选定 Spring AI 版本与一个模型完成文本调用、模拟工具调用、超时及用量验证；只使用样例内容。
4. 加入 AI 功能开关的设计：未配置密钥或功能关闭时，原系统仍可启动和使用。

**验收：**现有 88 个后端测试仍通过；前端可构建；模型兼容性有实际记录；全新数据库与已有数据库的迁移步骤分开。

### P1：完成解析闭环，4～6 天

1. 扩展服务端文件读取，接入 TXT/MD/PDF/DOCX 解析与分块。
2. 补齐 Worker、任务领取、版本校验、超时处理和受权重试。
3. 增加必要的来源位置字段，向前端提供解析状态。
4. 先用少量存量文档验证，再有界补扫其他符合条件的 `PENDING` 文档。

**验收：**上传后最终进入可解释的终态；重复解析不重复分块；软删、彻底删除与重试竞争不产生可检索的脏数据；重启不永久卡在 `PARSING`；失败不阻断原上传和下载。

### P2：实现可引用的检索，3～4 天

1. 增加正文 FULLTEXT 索引及空间限定查询。
2. 完成正文命中、分页读取、来源构造和引用失效处理。
3. 建立固定样例集，先测试检索而不调用模型。

**验收：**已知答案能检索到预期片段；其他空间、软删文档和非 READY 文档不可返回；分页和总长度有上限；真实 MySQL 验证而非只依赖 Mapper Mock。

### P3：实现只读 Agent 后端，4～6 天

1. 实现三个只读工具及显式受限循环。
2. 增加会话、消息、运行和工具调用记录。
3. 实现幂等提交、预算、取消、错误终态和来源校验。
4. 先提供完整结果接口与可查询追踪，不把前端流式效果作为后端调试前提。

**验收：**能根据首次工具结果继续检索或读取；能回答单文档及多文档问题；无资料时说明不足；模拟模型证明次数上限、非法工具、跨空间参数、超时、失权和重复请求均可控。

### P4：前端与流式状态联调，3～4 天

1. 增加空间内 Agent 入口、会话列表、输入和停止按钮。
2. 显示工具状态、最终回答、引用卡片及解析不可用提示。
3. 引用跳转复用文档预览；无精确页码时只展示真实支持的位置，不伪造定位。
4. 处理 401、SSE 断线、空间切换、旧事件丢弃和代理缓冲。

**验收：**完成一条“上传、解析、提问、查看工具过程、打开来源、追问”的完整流程；切换空间不串内容；代理环境下状态逐步可见；原工作台行为无回归。

### P5：只读 MVP 的质量与交付，3～4 天

1. 完成安全、检索和回答评测，修复影响主场景的问题。
2. 验证 AI 关闭、模型失败、Redis 配额故障和进程重启降级。
3. 完成数据库升级、Compose 配置、CI 与回退演练。
4. 更新 README 定位、架构图、真实限制及复现实例。

**验收：**达到第 11 节门槛，交付 V0.1。到这里已经是可展示的只读 Agent 项目，不必等待向量库或写操作。

### P6：受控标签操作，4～6 天

1. 增加标签读取和建议工具、待确认动作表、确认卡片。
2. 完成确认、拒绝、过期、权限重验、幂等和审计。
3. 验证状态变化和并发确认，不扩展更多写工具。

**验收：**未经确认数据库不发生标签修改；确认后至多产生一份标签关联；重复确认、权限撤销、标签删除、网络重试均得到明确结果。交付 V0.2。

### P7：效果驱动的可选优化，不计入首轮工期

只有固定评测显示关键词检索明显漏掉同义表达、且普通分词或查询改写不足时，才开展向量检索验证。

1. 用同一套样例比较关键词与语义检索，不凭演示个例决定。
2. 引入向量库时保留 MySQL 为事实来源，向量 payload 至少包含空间、文档、分块和解析版本。
3. 向量查询必须先按空间过滤，再回查数据库的权限、删除状态和当前版本。
4. 解析完成与向量可检索是两种状态，另设索引状态和可补偿任务；不能用 `READY` 同时表示两者。
5. 处理重解析、删除、模型维度变化、重建和失败重试；向量服务故障时允许退回关键词检索。

**排期参考：**V0.1 合计约 18～26 个有效开发日；V0.2 另需 4～6 天。兼职学习型开发通常需要更长日历周期，应以阶段验收而不是日期判断完成度。

## 11. 测试与评测

### 11.1 自动化测试分层

1. **保留现有回归。** 认证、成员、文件、标签、回收站和预览不能因为 Agent 改造失效。
2. **解析单测。** 空文件、中文、乱码、重复任务、无正文 PDF、异常文件、字数上限和切分边界。
3. **数据库集成测试。** 使用真实 MySQL 验证 FULLTEXT、事务回滚、版本条件更新、删除与发布竞争、唯一约束；Mock 测试不能证明这些成立。
4. **Agent 确定性测试。** 使用假的模型响应依次返回工具调用、错误参数、重复调用和最终回答，验证应用控制流程；CI 不依赖真实付费模型。
5. **API 与安全测试。** 非成员、其他用户的 session/run/action、模型伪造文档 ID、会话空间不符、执行中失权、历史来源失效。
6. **前端与代理测试。** 流事件边界、订阅注册期间恰好完成、断线、取消、401、空间切换和 HTML 注入；前端构建通过不代表这些场景通过。
7. **写操作测试。** 两个并发确认、超时后重试、动作过期、确认前资源变化、事务失败与审计关联。

### 11.2 固定评测集

准备至少 20 份无敏感信息的样例文档和 40 个问题，固定文档版本、预期来源与评分规则：

1. 15 个单文档事实问题。
2. 10 个跨文档比较或归纳问题。
3. 5 个资料不足、文档冲突或文档未就绪的问题。
4. 5 个权限边界与恶意文档指令问题。
5. 5 个多轮追问问题。

另建工具超限、取消、重试、服务不可用等确定性测试，不混在回答质量统计中。

建议首轮验收门槛如下，**这些是目标，不是当前已取得的成绩**：

1. 越权返回和未经确认写入为 0；任何一例都阻断交付。
2. 最终回答展示的引用编号 100% 可由后端解析，失效引用明确提示。
3. 有标准来源的检索问题中，至少 85% 能在 Top 6 找到关键证据；先计算检索质量，再评价生成质量。
4. 可回答问题中，人工检查至少 80% 的回答关键结论正确且有证据支持；逐条记录失败原因，不只报总分。
5. 所有“资料不存在”的固定样例都不得捏造确定答案；允许说明检索覆盖有限。
6. 如实记录总耗时、首次状态事件时间、模型与工具调用数、Token 及估算费用；在数据充分前不宣称 P95 或并发能力。

## 12. 数据迁移、部署与回退

1. `docker-entrypoint-initdb.d` 中的脚本只在首次初始化数据目录时执行。给 Compose 增加 SQL 挂载，不会自动升级已有 MySQL 卷。
2. 当前 `document_content.sql` 含 `DROP TABLE IF EXISTS`，只适合作为干净环境初始化的一部分，不能当作线上升级脚本执行。
3. 另设按版本编号的增量 SQL，记录执行状态；在备份恢复出的测试库上演练，校验列、索引和数据，再执行真实升级。不要使用 `down -v`“解决”迁移。
4. 首轮以新增表和兼容性字段为主，不同时移除旧接口或旧字段。应用回退前验证旧版本可读取升级后的数据库。
5. 将解析上限、执行器并发、Agent 调用上限、日额度、模型标识和 AI 开关纳入配置；密钥只通过环境变量或部署秘密注入，不提交到仓库。
6. 无密钥或 AI 关闭时不应因模型 Bean 初始化而导致后端启动失败。通过条件化配置和测试验证，而不是只隐藏前端入口。
7. 在现有 CI 中保留后端测试与前端构建，增加 AI Mock 测试；数据库集成测试需要明确启动 MySQL，不能默认为 CI 已有外部服务。
8. 部署仍沿用 GHCR 提交 SHA 镜像与 Compose 拉取，不引入 Kubernetes。外部模型故障不应让核心文档管理的健康检查失败。
9. 回退优先关闭 AI 功能，再恢复旧应用镜像；保留新增业务数据，禁止为了回退盲目删表。若版本间不兼容，按演练过的恢复步骤操作。
10. 会话和运行记录包含用户输入与文档衍生信息，上线前确定保留期限、用户清理方式和运维访问权限，不无限期保存全部调试内容。

## 13. 主要代码落点

以下是实施导航，不要求一次性建立所有类，更不要求为了目录整齐重构现有模块。

1. `teamdocs-backend/pom.xml`：模型接入、解析及测试依赖。

4. `service/impl/DocumentContentServiceImpl.java`：分块事务、条件发布与任务状态；不直接当成给模型调用的无权限工具。
5. `service/impl/DocumentServiceImpl.java`：上传、软删、恢复和彻底删除与正文生命周期衔接。
6. 新增解析 Worker、文本切分器和正文检索 Service；沿用现有 `service`、`impl`、`mapper` 分层，不先创建通用 Agent SDK。
7. 新增 Agent Controller、运行 Service、工具适配类及对应实体、Mapper、DTO、VO。
8. `aspect/SpaceRoleAspect.java`、`security/SpaceContext.java`：验证代理、异步和嵌套调用边界；只有新增调用方式确实需要时才调整。
9. `teamdocs-frontend/src/views`、`components`、`api`、`router/index.js`：空间 Agent 页面、来源卡片、状态流、确认卡片和路由入口。
10. `teamdocs-frontend/nginx.conf`、`application.yaml`、`.env.example`、`docker-compose.yaml`：流式代理、开关、预算和模型配置。
11. `sql/`：新安装脚本与独立增量迁移；`.github/workflows/ci.yml`：确定性测试和集成验证。
12. `README.md`、`PROGRESS.md`、`docs/DEPLOYMENT.md`：在功能实际验收后更新能力描述、开发中发现的问题和部署步骤，不提前把规划写成完成项。

后端代码落点均相对于 `teamdocs-backend/src/main/java/asia/creat/`，资源配置位于 `teamdocs-backend/src/main/resources/`。

## 14. 开始实施时的第一批任务

第一批只推进 P0 和 P1，不同时写聊天页面、向量库和操作工具。

1. 核对当前解析基础改动，补出已有数据库的非破坏性迁移方案。
2. 用小样例确认 Spring AI 与模型的工具调用兼容性，锁定精确依赖，保持普通文档功能不依赖模型可用性。
3. 打通“MinIO 流、TXT/Markdown 解析、分块、READY”的最短路径。
4. 补充失败、重试、任务版本、删除竞争和重启处理，再扩展 PDF/DOCX。
5. 用真实数据库证明解析结果与状态一致，再进入检索和 Agent 工具开发。

**完成标准不是新增了多少 AI 相关类，而是：用户提出一个空间内的文档任务，系统能安全地选择和执行必要工具，给出可核查结果，并在需要修改数据时等待用户确认。**
